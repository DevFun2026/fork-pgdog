# Workflow Retrospective

Convert observed friction into reviewed proposals, not silent policy mutation.

## When to use

- A completed task exposed repeatable workflow cost or a missed guardrail.

## Do not use

- Do not rewrite `.agent/policies/` or canonical skills automatically from one anecdote.

## Inputs

- Timeline, task evidence, failures/retries, review findings, user feedback, and relevant memory records.

## Steps

1. Compare intended workflow with observed sequence and evidence.
2. Identify root causes, repeated token/tool cost, missed signals, and controls that worked.
3. Separate project-specific learning from reusable workflow change.
4. Draft a proposal with benefit, tradeoff, compatibility, tests, and rollback.
5. Promote durable project learning through memory curation; change policy only after approval and verification.

## Stop conditions

- Stop before changing governance without explicit approval.

## Evidence

- Concrete events, commands, findings, measured impact, and affected artifacts.

## Output

- Retrospective plus bounded improvement proposals and memory candidates.

## Failure behavior

- Insufficient evidence produces a question or experiment, not a permanent rule.
